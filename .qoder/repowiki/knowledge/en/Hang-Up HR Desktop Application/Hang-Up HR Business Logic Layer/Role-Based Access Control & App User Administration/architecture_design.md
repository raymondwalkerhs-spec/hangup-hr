Three-layered RBAC model with clear dependency direction:
- `permission-catalog.js` is the immutable source of truth: it declares `ROLE_RANK`, `ROLE_ALIASES`, every feature-flag key in the `PERMISSIONS` array (with label/category/description), and computes a default boolean matrix via `defaultForRole`. It exports no DB code.
- `role-permissions.js` and `user-permissions.js` are symmetric persistence layers that load `app_role_permissions` / `app_user_permissions` from Supabase into an in-memory Map cache (60s TTL, deduplicated concurrent loads). They fall back to `permission-catalog.defaultForRole` when no override exists.
- `roles.js` is the public API consumed by controllers. Its internal `perm(key, userRole, legacyFn)` short-circuits per-user overrides first, then delegates to `role-permissions.isAllowedSync`, which itself falls back to the catalog's defaults. Every business capability (`canViewPayroll`, `canEditSale`, `canManageOrgStructure`, …) is implemented as a thin wrapper around `perm(...)` plus a legacy default function, so behavior can be toggled at runtime without code changes.
- `users-admin.js` sits on top of this stack: it manages the `app_users` table (CRUD, bcrypt password hashing, owner/IT flags, last-login timestamps), derives roles from employee IDs, syncs employee lead roles, and logs every mutation through `changelog.logChange`. It imports `normalizeRole` from `roles.js` and `MANAGEABLE_ROLES` from `permission-catalog.js` but never calls permission checks directly — it only mutates identity data.

Dependency direction: `users-admin.js` → `roles.js` → (`role-permissions.js` | `user-permissions.js`) → `permission-catalog.js` → `supabase-client`. The catalog has zero dependencies; the two override modules depend only on the catalog and Supabase; `roles.js` depends on both override modules plus `team-names` and `hrms-repo` for org-scoped filtering.
