Each file is a self-contained Node module exporting functions for one business entity (e.g. `companies-repo.js`, `it-requests-repo.js`). Every repo follows the same internal shape: a local `db()` helper wrapping `getSupabaseAdmin()`, an optional `requireSupabase()` gate that throws when `DATA_BACKEND` is not supabase, a `mapRow`/`mapXxx` mapper from snake_case DB rows to camelCase domain objects, and read/create/update/delete functions built on the Supabase JS client's `.from(...).select().insert().update().delete()` chain. Cross-cutting concerns are delegated outward: `business-repo.js` additionally depends on `./cache` for in-process caching of bonus/sales/expenses/bills, `./sales-working-day` for date math, and `./supabase-client`; `break-schedules-repo.js` calls `./settings-revision.bumpRevision()` after mutations; `companies-repo.js` falls back to seeded defaults when the `companies` table does not exist yet. Dependency direction is strictly inward — these repos depend only on shared infrastructure (`supabase-client`, `backend`, `cache`, `settings-revision`) and never import each other, so callers can pick individual repos without pulling the whole bundle.
