Two cooperating layers:
- `lib/cache.js` owns the local persistence: lazy-loaded `better-sqlite3` connection to `.cache/hr-cache.db`, schema created via `initSchema` (tables for employees, attendance/bonuses/deductions by month, position rates + monthly variants, config, payroll adjustments, commission types/tiers, documents, warnings, loans, loan payments, payroll splits, plus a key/value `meta` table). All writes go through `database.transaction(...)` batches; every row is stored as JSON in a `data TEXT` column with indexes on date/year_month/employee_id.
- `lib/data-store.js` is the public facade. It imports `backend.getBackend()` and `useSupabase()` to read/write the remote store, then calls `cache.set*` / `cache.upsert*` to keep the local DB authoritative. `syncFromSheet` runs a single `Promise.all` over all `backend.readAll*` endpoints, groups time-series rows by year-month via `groupByYearMonth`, merges locally edited attendance rows against remote rows using `isLocalAttendanceNewer` (prefers local when timestamps are missing but local has a real status), and seeds business tables (`sales`, `expenses`, `monthly_bills`, `bonus_requests`) only when `useSupabase()` is true. Mutations are serialized through a `mutationLock` promise chain so concurrent upserts do not race. Reads such as `readAttendanceEventsForMonth` always hit the local cache first to avoid Supabase replication lag.
- Supporting helpers: `lib/entity-mappers.js` normalizes spreadsheet column names into canonical fields consumed by `createEmployee`; `lib/id-generator.js` enforces unit/prefix rules (`UNIT_ID_RULES`, `BACKEND_POOLS`) and filters employees by promotion/departure/out status; `lib/settings-revision.js` keeps an in-process `memoryRevision` counter synced to the `app_settings_revision` Supabase table for cache-busting across processes.
