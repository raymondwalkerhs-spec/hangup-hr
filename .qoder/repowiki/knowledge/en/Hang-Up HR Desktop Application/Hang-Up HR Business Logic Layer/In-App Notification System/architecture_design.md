Five cooperating modules form a layered pipeline:
- `notify-store.js` is the persistence layer over Supabase (`app_notifications` table), exposing CRUD helpers (`createNotification`, `createNotificationsForUsers`, `readNotifications`, `markNotificationRead`, `markAllRead`) with graceful fallback when Supabase is disabled via `useSupabase()`.
- `notification-routing-config.js` holds admin-configurable routing rules keyed by `actionKey`; it loads them from `notification_routing_rules` with a 30s in-process cache and falls back to an embedded `DEFAULT_RULES` list when the table is missing or Supabase is off. `getRecipients(actionKey, {actor, context})` merges role-based recipients (resolved through `notifyRouting.resolveUsernamesByRoles`) with explicit usernames and actor exclusion.
- `notify-dispatch.js` is the thin orchestrator: callers invoke `dispatchNotification({actionKey, title, body, entityType, entityId, actor, context, type})`, which resolves recipients via the config and persists one row per recipient.
- `notify-routing.js` provides hard-coded audit/HR warning helpers (`auditNotify`, `hrWarning`, `notifyRegistrationSubmitted`, `notifySaleAssignment`) plus username resolvers (`resolveUsernamesForEmployees`, `resolveUsernamesByRoles`) used by both the config layer and other parts of the app; it also enforces exclusion of the CEO (`mark`) and the actor itself.
- `notifications.js` is the read-side aggregator: `collectNotifications(username, role)` fans out to multiple business sources (leave requests, loan requests, expenses, expiring documents) and persisted notifications, deduplicates by id/type-body, sorts by `createdAt`, and returns a flat array consumed by the UI.

Dependency direction is one-way: `notify-dispatch` → `notification-routing-config` → `notify-routing` → `notify-store` → Supabase client. The `notifications.js` collector depends on external repos (`hrms-repo`, `loan-requests-repo`, `business-repo`, `data-store`) but not on the dispatch/store side, keeping collection and dispatch decoupled.
