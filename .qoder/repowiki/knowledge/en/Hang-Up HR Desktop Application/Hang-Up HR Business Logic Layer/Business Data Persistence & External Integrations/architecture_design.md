- `backend.js` is the single switch: `getBackend()` returns `supabase-repo`, which implements the same read/write surface (`readEmployees`, `batchUpsertAttendance`, `upsertPayrollAdjustment`, …) that `data-store.js` expects. All business modules call `data-store.js`, which delegates persistence to `backend.getBackend()` and keeps an in-process `cache.js` (month-keyed) as the authoritative source of truth after every write.
- `storage.js` abstracts Supabase Storage uploads/downloads and signed URL generation; it is consumed by `documents.js`, `sale-attachment-storage.js`, and `pdf-export.js` so callers never touch the Supabase SDK directly.
- `airtable-client.js` plus the `airtable-*` helpers form a separate, opt-in REST client (gated by `AIRTABLE_SYNC_ENABLED`) used only by `airtable-sales-sync.js`; it does not participate in the main `data-store` path.
- `dropbox.js` provides upload/import/shared-link primitives used exclusively by the sales attachment pipeline (`sale-attachment-import-config.js`, `sale-submit-scope.js`).
- Cross-cutting concerns — change auditing via `changelog.js`, employee identity mapping via `employee-identity.js`, and month-profile merging via `month-profile.js` — are invoked from `data-store.js` after each mutation, ensuring every backend path logs consistently.
